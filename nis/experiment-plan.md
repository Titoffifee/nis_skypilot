# P17. План эксперимента

## Что сравниваем

Сравним долю размещённых задач, стоимость и время планирования при разном числе доступных машин. Ожидаем преимущество совместного выбора, когда часть задач привязана к конкретным локациям: гибкую задачу можно отправить к другому провайдеру, оставив дефицитную машину для привязанной.

| Метод | Как выбирает машины |
|---|---|
| Joint / SkyPilot-adapted | ILP размещает максимум задач у любых провайдеров, затем снижает стоимость |
| Fixed-provider | Тот же ILP, но с каталогом одного провайдера |
| Greedy-cheapest | Берёт задачи по порядку и выбирает самую дешёвую подходящую свободную машину. Если подходящей машины нет, пропускает задачу и продолжает |

Основной провайдер для Fixed-provider — A. B и C проверим отдельно. Для Greedy при равной цене выбираем по идентификатору машины; влияние порядка задач проверим перестановками.

## Как работает ILP

В [авторском ILP](https://github.com/skypilot-org/skypilot/blob/fff7b16adc0cad0626afbbcfa469d4704978d4e8/sky/optimizer.py#L580) каждой задаче назначается один ресурс. В нашей версии назначение можно пропустить, если машин не хватает. Сначала максимизируем число назначений, затем минимизируем их стоимость.

`x[j,r]` равно 1, если задача j назначена ресурсу r. Рассматриваем только ресурсы, подходящие по CPU, локации и сроку:

```text
sum_r x[j,r] <= 1                   для каждой задачи j
sum_j x[j,r] <= capacity[r]         для каждого ресурса r

1. maximize sum_(j,r) x[j,r]
2. Зафиксировать найденное число назначений и минимизировать:
   sum_(j,r) x[j,r] * duration_h[j] * price_usd_h[r]
```

На оба этапа даём 30 секунд суммарно. Если время истекло, сохраняем найденный план и отмечаем отсутствие доказанного оптимума. При нулевом числе назначений второй этап не нужен.

Эта модель сводится к максимальному потоку минимальной стоимости: каждая размещённая задача отправляет единицу потока в подходящее предложение, ёмкость предложения равна числу машин. Используем ILP, поскольку исследуем адаптацию оптимизатора SkyPilot.

## Каталог и задачи

Используем синтетический каталог: 3 провайдера × 3 региона × 3 типа машин с 2/4/8 CPU. У каждого из 27 предложений исходно 8 машин, всего — 216. A/B/C не обозначают реальные облака.

Цена в USD/ч:

```text
0.05 * cpus * provider_factor * region_factor * jitter
```

Множители провайдера: `{0.9, 1.0, 1.2}`, региона: `{0.8, 1.0, 1.3}`. `jitter` равномерно распределён на `[0.9, 1.1]`.

Для задач равновероятно выбираем CPU из `{2,4,8}`, длительность — из `{0.5,1,2}` часов. Срок равен длительности. В основных сериях он не ограничивает выбор машины; невозможный срок проверяем отдельно на ручном случае. Все задачи стартуют одновременно и занимают по одной машине; остальные упрощения описаны в [проекте](project.md#упрощения).

| Набор | Разрешённые локации |
|---|---|
| Без привязок | Весь каталог |
| С привязками | 20% задач — весь каталог, 30% — один случайный провайдер, 50% — одна случайная пара «провайдер, регион» |
| Контрольный | Весь каталог, одинаковая цена за CPU; у каждого провайдера машин каждого размера не меньше числа задач с таким требованием CPU. Дефицит не применяем; ожидаем совпадение стоимости методов |

Размеры наборов: 50, 100 и 200 задач. Входы сохраняем и подаём всем методам одинаковыми.

У A исходно 72 машины, поэтому Fixed-provider не разместит 100 или 200 задач даже без дефицита. Задачи с привязкой к другим провайдерам он также пропустит. Это учитываем при сравнении доли размещённых задач.

## Дефицит и серии запусков

Удаляем долю машин `s ∈ {0, 0.1, 0.25, 0.5, 0.75}`. Для каждого seed перемешиваем список машин и удаляем первые `floor(s * 216)`. При увеличении дефицита ранее удалённые машины не возвращаются. Цены и задачи остаются прежними.

Основная серия:

```text
2 набора задач × 3 размера × 5 уровней дефицита
× 20 seeds (0..19) × 3 метода = 1800 запусков
```

Контрольный набор проверим отдельно. Дополнительные серии — Fixed-provider с B/C, удаление машин сначала у A, затем у B и C, а также по пять перестановок задач для Greedy. Для них берём 100 задач, те же seeds и уровни дефицита.

Сначала проведём пробную серию: 50 задач, `s=0/0.5`, seeds `100..102`. Проверим время, память и наличие конкуренции за машины. Если диапазон дефицита окажется неудачным, скорректируем его до основных серий. Используем доступный компьютер, указанный в [описании проекта](project.md#ресурсы-и-ближайшие-шаги).

## Что измеряем

| Показатель | Как считаем |
|---|---|
| Доля размещённых задач, % | Число задач с допустимым назначением / число задач на входе × 100 |
| Доля полностью размещённых наборов, % | Число входов, где размещены все задачи / число входов серии × 100 |
| Стоимость плана, USD | Сумма стоимостей размещённых задач |
| Время планирования, с | Время работы метода без генерации данных, импорта и проверки плана |

Стоимость сравниваем на одинаковых входах при одинаковом числе размещённых задач; полные планы показываем отдельно. Ошибки и остановки по времени отмечаем отдельно. Неверные планы исключаем из расчёта метрик, указывая их число. Если план не найден до остановки, долю задач не считаем и отмечаем пропуск.

## Проверка и обработка результатов

Валидатор проверяет CPU, локацию, срок, число занятых машин и стоимость. У каждой размещённой задачи должно быть ровно одно назначение; остальные задачи могут отсутствовать в плане.

Ручные случаи включают отсутствие подходящих машин, нулевую ёмкость, невыполнимый срок, равные цены и конфликт гибкой и привязанной задач. На входах до 8 задач и 4 предложений сравниваем ILP с полным перебором. При увеличении ёмкости оптимальное число назначений не должно уменьшаться. Если оно не изменилось, стоимость не должна расти. Первые проверки описаны в [отчёте КТ-1](checkpoints/01.md).

Для каждой конфигурации усредняем долю задач по входам с корректными планами и считаем долю полностью размещённых наборов среди всех 20 входов. Рядом указываем число ошибок и пропусков. Сравниваем методы попарно на тех же входах. Для разниц строим 95% bootstrap-интервалы по входам: 10 000 повторных выборок, seed=2026. Для стоимости указываем число входов, на которых сравнение возможно.

Время измерим отдельно: 100 задач, `s=0/0.5`, seeds `0..4`, по пять запусков в новых процессах. Порядок методов будем менять. Покажем медиану и диапазон p10–p90.

Построим графики доли размещённых задач и полных наборов от дефицита, стоимости и времени расчёта. Разные размеры и наборы задач анализируем отдельно. Сохраним входы, планы и измерения, чтобы можно было разобрать отличия между методами.

Генератор и массовый запуск пока не готовы; основные серии ещё не проводились.
